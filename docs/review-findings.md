# レビューで確認した元の MicroPython 実装の問題

`legacy/bme280_calibrated.py` をレビューした際、`machine` / `time` をスタブした
実行ハーネスを用意し、**実際に動かして確認した**問題をまとめたものです。
推測ではなく、例外・実測値・レジスタマップの突き合わせで裏取りしています。

レビュー全体では 18 件（CRITICAL 6 / HIGH 7 / MEDIUM 3 / LOW 2）を指摘しました。
以下は、そのうち実行またはデータ比較で確定した主要なものです。

---

## CRITICAL

### 1. `dig_H5` を参照するが取得していない（起動時に落ちる）

湿度補償計算で `calib["dig_H5"]` を参照しますが、校正読み出しは `dig_H4` までしか
設定していません。最初の測定で `KeyError` / `AttributeError: dig_H5` で停止します。

BME280 の湿度校正係数は `0xE1..0xE7` にあり、H4 と H5 は **1 バイトにニブル分割で
 packed**されています。

```
H4 = (int8)h[3] * 16 | (h[4] & 0x0F)
H5 = (int8)h[5] * 16 | (h[4] >> 4)
```

C++ 実装ではこの結合を `readCalibration()` で正しく行い、ホストテストで検証しています。

### 2. 気圧校正係数を誤ったレジスタ領域から読み出している

気圧の `dig_P1..dig_P9` は **0x8E..0x9F** にあります。元コードは **0xE8..0xF8**
（制御・状態レジスタの領域）から読み出していました。

読み出し先が物理的に違うため、値は制御ビットの残骸であり、気圧計算は完全に無意味です。
この種のバグは「値がおかしい」ではなく「値が常に同じ・極端」として現れます。

### 3. 温度と気圧の ADC 値が入れ替わっている

BME280 の出力レジスタは **気圧が先**です。

```
0xF7  press MSB
0xF8  press LSB
0xF9  press XLSB
0xFA  temp MSB
0xFB  temp LSB
0xFC  temp XLSB
0xFD  hum MSB
0xFE  hum LSB
```

元コードは 0xF7 を温度として扱っていたため、温度と気圧が入れ替わっていました。
C++ 実装では 0xF7 から 8 バイトのバースト読み出しを行い、この順序をテストで固定しています。

### 4. `ctrl_hum`（0xA2）に書き込んでいない

湿度のオーバーサンプリングは `ctrl_meas` ではなく `ctrl_hum` で設定します。
しかも **`ctrl_hum` を `ctrl_meas` より先に書く**必要があります（`ctrl_meas` の書き込み時に
湿度設定が確定するため）。

元コードは `ctrl_hum` を一度も書いておらず、湿度のオーバーサンプリング設定が不定でした。
C++ 実装では順序を明示し、書き込み順序を検証するテストを入れています。

### 5. `t_fine` のスケールが約 680〜920 倍ずれている

Bosch 参照実装の温度補償は **16 ビット固定小数**で動作します。

- `compensate_temperature()` は **0.01 °C 単位**（centi-°C）を返し、`t_fine` を設定する
- `compensate_pressure()` は `t_fine` を使い、**Pa × 100** を返す（64 ビット演算）
- `compensate_humidity()` は `t_fine` を使い、**%RH × 1024** を返す

つまり **必ず温度から先に補償する**必要があります。元コードは異なるスケールを混用し、
`t_fine` が約 680〜920 倍ずれていました。

### 6. `float >> int` で `TypeError`

補償計算は整数演算前提ですが、float をシフトしようとして `TypeError` になっていました。

## HIGH

### 7. `adc_P` を読み出しているが計算に使っていない

気圧の ADC 値を取得しているのに、補償計算に渡していません。

### 8. 露点計算で対数の底が不一致

Magnus 式は自然対数（`exp`）用の定数で定義されます。元コードは `exp()` 用の定数に対して
`pow(10, ·)` を使っており、底が不一致でした。C++ 実装は `exp()` / `log()` を使います。

## 実装時の追加で分かった pico-sdk の罠

レビュー対象の Python ではなく、C++ へ書き換えた側で踏んだものはこちらです。
詳細は [../firmware/README.md](../firmware/README.md) の "Two traps" 節。

1. `i2c_write_blocking(i2c, addr, nullptr, 0, false)` は **何も送信せず全アドレスに成功を返す**
   （`len == 0` で書き込みループの本体が一度も実行されない）。
2. `n += snprintf(buf + n, sizeof(buf) - n, ...)` は **サイズ引数がラップアラウンド**する
   （`snprintf` は切り詰め前の必要長を返す）。

1 が 2 を誘発し、スタック溢れで RP2350 がハードフォールト、USB デバイスがバスから消えました。
